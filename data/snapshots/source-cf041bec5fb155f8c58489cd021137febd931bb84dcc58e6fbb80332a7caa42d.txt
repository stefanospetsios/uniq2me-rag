REST and REST APIs: A Complete Guide for Developers



          

            Learn what REST and REST APIs are, the six REST principles, HTTP methods, security patterns, and how to manage REST APIs at scale across gateways.

Fast Facts




  

    


REST 
represents an architectural style for distributed systems, established by Roy Fielding in 2000. It is not a protocol or standard.




A REST API is any interface complying with REST's six constraints: uniform interface, statelessness, client-server separation, cacheability, layered system, and code on demand (optional).




REST APIs utilize HTTP methods (GET, POST, PUT, PATCH, DELETE) to manipulate resources identified by URIs, typically swapping JSON.




"REST API" and "RESTful API" are used interchangeably. "RESTful" suggests stricter compliance with all six constraints.




In production, REST APIs require more than authentication libraries. They demand gateway-enforced security, federated governance, observability, and lifecycle management.

Many developers can define REST in a single line. Fewer can articulate why their REST API halts under pressure, fails a compliance check, or malfunctions when integrating with a Kafka stream or an AI agent. The distance between knowing REST and operating REST APIs in production exceeds what most content suggests.






This manual addresses both areas. You will receive the basics of REST and REST APIs, the six constraints defining the style, daily HTTP methods, and REST comparisons against options like SOAP, GraphQL, and event-driven models. You will also encounter production realities: securing REST APIs at scale, governing them across various gateways, and linking them to the agent-driven systems your company is beginning to construct.




What is REST?




REST signifies Representational State Transfer. It is an architectural style for distributed hypermedia systems, presented by Roy Fielding in his 2000 doctoral thesis at UC Irvine. Fielding was a lead author of the HTTP specification, and REST evolved directly from that effort.




A few things REST is not, since confusion remains constant:






REST is not a protocol. HTTP is a protocol. REST is a collection of constraints applicable when building systems atop protocols like HTTP.




REST is not a standard. No governing body certifies an API as RESTful. Compliance exists on a spectrum.




REST is not identical to HTTP. While most REST APIs operate over HTTP, REST could theoretically apply to other protocols.






REST defines a set of architectural constraints that, when adhered to, yield systems with specific traits: scalability, evolvability, visibility, portability, and reliability. Fielding argued the web succeeded because it followed these constraints. Applying the same constraints to APIs yields similar advantages.




The practical outcome is that REST provides a shared vocabulary and design conventions. When two developers claim they are building a REST API, they usually mean the same thing, despite no committee enforcing it.




What is a REST API?




A REST API is any interface conforming to REST's architectural constraints. Practically, this means an API exposing resources at URIs, using HTTP methods to operate on them, and exchanging representations (usually JSON, sometimes XML) over HTTP.




A standard REST API call appears as follows: a client sends GET https://api.example.com/orders/12345 and the server returns a JSON document detailing order 12345. To create a new order, the client sends a POST containing order data in the request body. To update it, use PUT or PATCH. To remove it, DELETE. This pattern remains consistent across every REST API you have used.




REST APIs dominate the pattern for web and mobile backends, microservice communication, and SaaS integrations. If you called a public API in the last decade, it was likely REST. Stripe, GitHub, Twilio, Salesforce, and most cloud providers expose REST APIs as their main interface.




You will see "REST API" and "RESTful API" used interchangeably. A technical distinction exists (covered in a dedicated section below), but in daily conversation they mean the same thing.




The Six Principles of REST




Fielding defined six constraints an API must follow to qualify as RESTful. Five are mandatory. The sixth is optional. Together they generate the properties REST is known for.




Uniform interface




The uniform interface is the core constraint distinguishing REST from other architectural styles. It contains four sub-constraints:






Resources are identified by URIs.
 Every significant entity (an order, a user, a product) possesses a stable URI.




Resources are manipulated through representations.
 The client interacts with a representation of the resource (JSON, XML, HTML), not the resource directly.




Messages are self-descriptive.
 Each request and response carries sufficient metadata (HTTP method, status code, headers, content type) to be understood without external context.




HATEOAS (Hypermedia as the Engine of Application State).
 Responses include links indicating what actions are available next to the client. Most APIs labeled REST do not implement this fully.






Client-server separation




The client and server hold distinct responsibilities. The client owns the user interface and user state. The server owns data storage and business logic. This separation allows them to evolve independently. You can rewrite the mobile app without touching the backend, or migrate the database without altering the API.




Statelessness




Every request from a client must contain all information the server needs to process it. The server does not store session state linked to a specific client between requests. Authentication, for instance, gets sent with every request (typically as a bearer token in the Authorization header) rather than being held in a server-side session.




Statelessness enables REST APIs to be horizontally scalable. Any server can handle any request, allowing load balancers to route traffic anywhere without sticky sessions.




Cacheability




Responses must declare whether they can be cached and for how long. Cache directives travel within HTTP headers (Cache-Control, ETag, Expires). Executed well, caching drastically reduces server load and client latency. Executed poorly, it serves stale data and creates debugging nightmares.




Layered system




A client cannot tell if it is communicating directly with the origin server or an intermediary. Load balancers, CDNs, reverse proxies, and API gateways sit between client and server without changing the contract. This is exactly the constraint enabling API gateways, which we will revisit.




Code on demand (optional)




Servers can optionally ship executable code to clients (JavaScript, applets) extending client functionality. This is the single constraint REST treats as optional, and in practice, almost no one uses it for API design.

How REST APIs Work




A REST API call follows a predictable lifecycle. The client constructs an HTTP request targeting a specific URI, the server processes it, and a response returns with a status code and (usually) a body.




A request comprises four parts:






Method
: GET, POST, PUT, PATCH, DELETE, and a few others.




URI
: identifies the resource, e.g., /api/v1/orders/12345.




Headers
: metadata such as Authorization, Content-Type, Accept, Cache-Control.




Body
: optional payload for methods like POST, PUT, and PATCH. Typically JSON.






A response has three components:






Status line
: HTTP version plus a status code (200 OK, 201 Created, 400 Bad Request, 401 Unauthorized, 404 Not Found, 500 Internal Server Error).




Headers
: metadata regarding the response (content type, length, cache directives).




Body
: the resource representation, typically JSON.






The server authenticates the request, validates input, applies business logic, fetches or modifies data, and returns the result. Between client and server you often find intermediaries: a load balancer, a CDN, an API gateway enforcing rate limits and authentication, and observability tools capturing metrics. The layered system constraint enables that stack.




JSON has become the de facto representation format. It is lighter than XML, native to JavaScript, and well-supported in every language. XML still appears in regulated industries and older systems.




HTTP Methods in REST APIs




REST maps HTTP methods to CRUD operations. The mapping is conventional, not enforced, but you should follow it.






GET
: Read a resource. Safe (does not modify state) and idempotent (calling it many times has the same effect as calling it once). Responses are cacheable.




POST
: Create a resource, or trigger an action that doesn't fit the other methods. Not idempotent. Calling POST twice typically creates two resources.




PUT
: Replace a resource entirely. Idempotent. PUT-ing the same payload ten times leaves the resource in the same state as PUT-ing it once.




PATCH
: Partially update a resource. Often idempotent in practice, though the spec doesn't require it.




DELETE
: Remove a resource. Idempotent. Deleting an already-deleted resource should return the same result.






Idempotency matters because networks are unreliable. A client receiving no response cannot tell if the request succeeded or failed. If the method is idempotent, the client can safely retry. If not (POST), the client risks creating duplicate resources. That is why payment APIs often require an Idempotency-Key header on POST requests.




A few less common methods round out the set: HEAD (like GET but returns headers only), OPTIONS (discover what methods a resource supports, used heavily in CORS preflight), and TRACE (rarely used, often disabled for security reasons).




REST API vs RESTful API: Is There a Difference?




In day-to-day conversation, no. The terms get used interchangeably.




The technical distinction lies in strictness. A RESTful API adheres strictly to all of REST's required constraints, including HATEOAS. A REST API is the looser, everyday usage covering anything exposing resources over HTTP with JSON and using HTTP methods conventionally.




Leonard Richardson proposed a four-level maturity model capturing the spectrum:
















Level








Description








Example
















0








Single URI, single method (usually POST). Effectively RPC over HTTP.








Many older SOAP-style APIs












1








Multiple resources at distinct URIs, but still one method.








Some legacy APIs












2








Resources plus correct use of HTTP methods and status codes.








Most APIs called REST












3








Level 2 plus HATEOAS (hypermedia controls in responses).








GitHub API (partially); most APIs don't reach this level




















Most APIs in production sit at Level 2. They use HTTP methods correctly, return appropriate status codes, and structure URIs around resources, but they don't embed hypermedia links. Strictly speaking, those APIs aren't fully RESTful, but the industry calls them REST anyway and the term has stuck.




For practical purposes, treat the terms as synonyms. If someone insists on the distinction, they are usually arguing about HATEOAS.




Benefits of REST APIs




REST's benefits flow directly from its constraints:






Scalability
: Statelessness means any server can handle any request. Horizontal scaling becomes trivial. Caching reduces backend load further.




Flexibility
: Client-server separation lets the front end and back end evolve independently. You can rewrite a mobile app without changing the API, or refactor the backend without breaking clients.




Platform independence
: REST runs on HTTP and uses JSON, which every modern language, runtime, and platform supports. A Python backend can serve a JavaScript front end and a Swift mobile app from the same API.




Simplicity
: Standard HTTP verbs and readable URIs make REST APIs easy to learn, document, and debug. You can explore most REST APIs with curl or a browser.




Tooling
: The ecosystem is massive. OpenAPI for specifications, Postman for testing, every API gateway on the market for management. You won't find tooling gaps.






These benefits explain why REST became the default. They also explain why REST has held its position against successive challengers like SOAP, GraphQL, and gRPC.




REST API Authentication and Security




A REST API in production needs authentication, authorization, transport security, and protection against abuse. The mechanisms have matured into a small set of well-known patterns:






API keys
: A static secret sent in a header (Authorization: Bearer <key> or X-API-Key: <key>). Simple to implement, easy to leak. Best for server-to-server traffic with low sensitivity, or as a first step for public APIs.




Basic Authentication
: Username and password base64-encoded in the Authorization header. Effectively obsolete for new APIs. Still appears in legacy systems.




OAuth 2.0
: Token-based authorization framework. The client obtains a short-lived access token from an authorization server and presents it on each request. Standard for delegated access, third-party integrations, and most modern public APIs. OAuth 2.1 consolidates best practices and removes deprecated flows.




JWT (JSON Web Tokens)
: A token format, often used as the access token in OAuth flows. Self-contained and signed, so the API can verify them without a database lookup. Watch the expiration and revocation story carefully.




mTLS (mutual TLS)
: Both client and server present X.509 certificates during the TLS handshake. Strong machine-to-machine authentication. Common in financial services, healthcare, and any system that needs FAPI-grade security.






That covers authentication. You also need authorization (what is this caller allowed to do?), rate limiting (how do you stop one consumer from overwhelming the API?), input validation (how do you reject malformed or hostile requests?), and observability (how do you know what's happening in production?).




Here is the part most tutorials skip: implementing all of this in application code, per service, doesn't scale. If you have ten REST APIs, you have ten places where authentication logic lives, ten places where rate limiting gets configured, and ten places where the inevitable security update has to ship. Inconsistency is how shadow APIs and audit failures happen. This is where API gateways earn their place, enforcing authentication, OAuth flows, mTLS, rate limiting, and threat protection centrally so application teams stop writing the same security logic over and over.




REST vs SOAP, GraphQL, and Event-Driven APIs




REST isn't the only option. The alternatives each solve a specific problem REST handles poorly.
















Style








Format








Best for








Tradeoffs
















REST








JSON over HTTP








Resource-oriented APIs, broad client diversity








Over-fetching, under-fetching, request-response only












SOAP








XML over HTTP (or other transports)








Regulated industries, contract-heavy integrations, WS-* security








Verbose, heavier tooling, slower to evolve












GraphQL








Single endpoint, query language








Client-shaped queries, complex object graphs, mobile apps minimizing payload








More complex caching, query cost analysis required, learning curve












Event-driven (Kafka, MQTT, WebSocket, SSE)








Binary or text streams, depends on broker








Real-time data, pub/sub, high-frequency events, async workflows








Different mental model, separate infrastructure, harder to govern




















SOAP remains common in banking, insurance, and government systems where contracts and WS-Security matter. GraphQL has found a strong niche in front-end-heavy applications where the cost of multiple REST round trips becomes painful. Event-driven patterns dominate when you need real-time data, push semantics, or high-throughput streams.




Real architectures combine these styles. A typical enterprise stack today runs REST APIs for 




synchronous interactions, Kafka or MQTT for event streams, and occasionally GraphQL at the edge for mobile clients. Governing all of them through separate tools is how policy drift starts. Unifying them under one control plane is what platform teams increasingly look for.




When to Use REST APIs




REST fits well when:






Your data model is resource-oriented (users, orders, products, documents).




Request-response is acceptable. Most CRUD-style workloads qualify.




You need broad client compatibility across web, mobile, and server-to-server.




Caching at the HTTP layer would benefit you (read-heavy workloads).




You want maximum tooling and ecosystem support.






REST is a poor fit when:






You need real-time push from server to client. Use WebSocket or Server-Sent Events.




You're streaming high-frequency events to many consumers. Use Kafka, MQTT, or similar.




Clients need fine-grained control over response shape to avoid over-fetching. Consider GraphQL.




You need continuous bi-directional communication, such as chat or collaborative editing. Use WebSocket.




Interactions span long-running workflows with multiple participants. Consider event-driven or workflow-based patterns.






A pragmatic rule: start with REST. Add other styles when you hit a problem REST genuinely can't solve, not because the alternative is fashionable.




Managing REST APIs at Scale




One REST API is easy. Fifty REST APIs across four teams, three clouds, and two acquired companies is where things break. The challenges shift from how do I build a REST API to how do I keep all of them secure, discoverable, observable, and consistent.




API gateways
 solve the first layer of the problem. A gateway sits between clients and your REST APIs and enforces cross-cutting concerns centrally: authentication (OAuth 2.0, JWT validation, mTLS, API keys), rate limiting and quotas, request and response transformation, threat protection, caching, and observability. Instead of every service implementing OAuth flows in code, the gateway handles it once and applies the policy uniformly.




Federated governance
 is where most North American enterprises actually live. You are probably not running a single gateway. You have AWS API Gateway in front of some Lambda functions, Apigee from an earlier modernization effort, Azure API Management for the analytics platform, and maybe IBM API Connect or Kong somewhere in the back. Ripping all of that out is rarely realistic. What you need is a control plane that can discover, catalog, and govern APIs across all of those gateways without forcing a migration. This is what federated API management delivers: one set of policies, one developer portal, one audit trail, applied consistently over the multi-gateway environment you already have. Gravitee's Federated API Management approach works this way, federating governance across AWS API Gateway, Apigee, Azure API Management, IBM API Connect, Confluent, and Solace alongside Gravitee's own gateway.




Developer portals
 address the discovery problem. A REST API nobody can find is a shadow API waiting to happen. A portal gives internal developers, partners, and external consumers a self-service catalog with documentation, interactive testing, subscription plans, and usage analytics. When portals span every gateway in your environment, you stop the duplicate-build pattern where a team writes a new service because they didn't know one already existed.




Lifecycle management
 ties it all together. APIs need to be designed, deployed, versioned, observed, and eventually retired. Doing that through Terraform or a Kubernetes operator (rather than clicking through UIs) is what lets platform engineering teams keep up as the API footprint grows.




REST APIs in Modern Architecture




REST APIs used to have two consumers: browsers and mobile apps. That is no longer true. Today, REST APIs are consumed by microservices calling each other, by event-driven workflows that fan out to dozens of downstream services, and increasingly by AI agents.




The AI consumer is the part most articles miss. When an agent built on a framework like LangChain or invoked through Anthropic's Claude or OpenAI's tool-use APIs needs to take an action in the real world, it does so by calling an API. The Model Context Protocol (MCP) has emerged as a standard way for agents to discover and invoke tools, and most of those tools are wrappers around REST APIs.




This changes the governance picture. A human consumer typing into a UI moves slowly and gets rate-limited by usage patterns. An agent can fire hundreds of requests per second, chain calls across systems, and operate with broader permissions than any individual user. The questions that used to be theoretical (which agent called this API? was it authorized? did it exceed its budget?) are now operational.




The interesting question for 2026 isn't what is REST. It's how do you govern REST APIs when an autonomous agent is the consumer. That involves giving agents distinct identities (not shared service accounts), enforcing tool-level scopes (not blanket access), and observing agent behavior with the same rigor you apply to human users. Gravitee's Agent Tool Server exposes existing REST APIs as MCP-compliant tools without backend changes, so the REST APIs you already have can become governed agent tools through configuration rather than rewriting.




REST isn't going anywhere. The protocol is too entrenched, the tooling too mature, and the developer mental model too well-established to be displaced. What's changing is the surrounding architecture: more consumers, more protocols alongside it, and stricter governance demands.




Frequently Asked Questions









  
  




      

        Is a REST API the same as a RESTful API?
        

      

    

  



  

    
In everyday usage, yes. Technically, "RESTful" implies strict adherence to all six REST constraints, including HATEOAS. Most APIs called REST sit at Level 2 of the Richardson Maturity Model, meaning they use resources and HTTP methods correctly but skip hypermedia. The industry treats the terms as synonyms.



  



  
  




      

        What is a simple example of a REST API?
        

      

    

  



  

    
Public examples include the GitHub API (GET https://api.github.com/users/octocat), the Stripe API (POST https://api.stripe.com/v1/charges), and most public weather services. Each exposes resources at URIs, uses HTTP methods conventionally, and returns JSON.



  



  
  




      

        Can REST APIs handle real-time data?
        

      

    

  



  

    
REST is request-response by design, so it isn't the right tool for true real-time push. For real-time scenarios, use WebSocket for bi-directional channels, Server-Sent Events for server-to-client push, or an event broker like Kafka or MQTT for high-throughput streams. A modern API platform should govern REST alongside these protocols rather than treating them as separate worlds.



  



  
  




      

        How do you secure a REST API in production?
        

      

    

  



  

    
OAuth 2.0 (or 2.1) for delegated access, mTLS for high-assurance machine-to-machine traffic, and JWT for self-contained tokens. Add rate limiting, input validation, and gateway-level enforcement so the same policies apply to every API. Implementing authentication libraries per service doesn't scale and creates inconsistency that audits catch.



  



  
  




      

        What is the difference between REST and GraphQL?
        

      

    

  



  

    
REST exposes multiple resources at distinct URIs and uses HTTP methods to operate on them. GraphQL exposes a single endpoint and lets clients send queries that specify exactly which fields they want. REST is simpler and benefits from HTTP caching. GraphQL reduces over-fetching for clients with complex needs. Most architectures use both: REST for general-purpose APIs and GraphQL where client query flexibility matters.



  



  
  




      

        Do REST APIs require an API gateway?
        

      

    

  



  

    
Not strictly. A handful of internal services can run without one. Beyond that, a gateway becomes essential for centralizing authentication, rate limiting, observability, and policy enforcement. Once you're running APIs across multiple teams, gateways, or clouds, federated API management becomes the practical way to keep governance consistent without ripping out your existing infrastructure.



  



  




















 




Understanding REST is the easy part. Running REST APIs in production, across teams, gateways, and consumers (human and agent alike) is where most architectures break. If that sounds like the problem you're actually trying to solve, see how Gravitee's federated API management handles it across your existing stack.
