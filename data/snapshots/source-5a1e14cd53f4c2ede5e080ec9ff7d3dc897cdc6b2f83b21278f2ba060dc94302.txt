Connection Response Codes


Section titled “Connection Response Codes”










Code


Meaning










0x00


Connected successfully






0x01


Unacceptable protocol version — the server doesn’t support the requested MQTT protocol level






0x02


Identifier rejected — for plain (non-TLS) connections, the Client ID was empty or malformed. For a client connecting over the X.509 SSL port, this code is also returned when 
no client certificate reached the server during the TLS handshake
 — see the note below before assuming your Client ID or certificate CN is the problem






0x03


Server unavailable — the server is not currently able to accept connections






0x04


Bad username or password — access token missing or malformed






0x05


Not authorized — access token invalid or device disabled. Over the X.509 SSL port, this code also covers a client certificate that 
was
 received but whose fingerprint doesn’t match any registered device credential









	

		
X.509: telling code 2 and code 5 apart
	



	
	
ThingsBoard’s MQTT SSL listener accepts the TLS handshake even if the client never presents a certificate — mutual TLS is optional at the handshake level, not enforced. That means:




Code 2 (Identifier Rejected)
 means no client certificate arrived at all. The connection silently fell back to plain Client-ID-based authentication and failed. This is a TLS/client configuration issue, not a Client ID or Common Name mismatch — check whether your client is actually configured to present its certificate during the handshake.




Code 5 (Not authorized)
 means a certificate 
was
 received, but ThingsBoard couldn’t find a matching device. How that match happens depends on which X.509 method you’re using: with the 
Individual Certificate
 method, matching is based entirely on the certificate’s content, never on its Common Name or the MQTT Client ID — ThingsBoard computes a SHA3-256 hash of the certificate (markers and line breaks stripped) and looks up a device credential with that exact fingerprint. With the 
Certificate Chain
 method, the device is instead identified by extracting its name from the certificate’s Common Name via the configured regex (see 
Certificate Chain
 above) — so a CN/regex mismatch there is a valid thing to check.




If you see code 2, first confirm your client is sending its certificate at all (a TLS trace or your MQTT library’s debug logging will show this). Only look at Client ID or CN once you’ve confirmed a certificate is actually being sent — but even then, the certificate’s content, not the CN, is what determines the device match for the Individual Certificate method.
